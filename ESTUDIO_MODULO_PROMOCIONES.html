¿Qué hace este módulo? Permite crear descuentos temporales aplicados a un producto específico o a una categoría completa. Cuando el POS carga, recibe todas las promociones vigentes y las aplica automáticamente al calcular el precio final sin ninguna interacción adicional del vendedor.
2. Flujo Completo — Paso a Paso Frontend → Backend → BD
1
Usuario abre el módulo Promociones
PromocionesPage.jsx — useEffect → fetchAll()
Frontend

Al montar el componente, el hook useEffect([], []) llama a fetchAll(), que hace un solo request al endpoint de inicialización y recibe de golpe las promociones, los productos y las categorías.

// PromocionesPage.jsx — carga inicial
const fetchAll = async () => {
  try {
    setLoading(true);
    const res  = await api.get('/promociones/init');
    const data = res.data?.data ?? {};

    setPromociones(Array.isArray(data.promociones) ? data.promociones : []);
    setProductos(  Array.isArray(data.productos)   ? data.productos   : []);
    setCategorias( Array.isArray(data.categorias)  ? data.categorias  : []);
  } catch (err) {
    toast.error('Error al cargar promociones');
  } finally {
    setLoading(false);
  }
};

useEffect(() => { fetchAll(); }, []);  // [] = solo al montar
2
Backend responde con 3 catálogos en un solo request
PromocionController::init() — GET /api/promociones/init
Backend

El método init() carga todas las promociones con sus relaciones (Eager Loading), más los selectores para el formulario.

public function init(): JsonResponse
{
    // Eager Loading: with() evita el problema N+1
    $promociones = Promocion::with([
            'producto:id,nombre,codigo',  // solo 3 campos
            'categoria:id,nombre'          // solo 2 campos
        ])
        ->orderBy('created_at', 'desc')
        ->get();

    // Solo id+nombre+codigo para el selector del form
    $productos = Producto::where('activo', true)
        ->orderBy('nombre')
        ->get(['id', 'nombre', 'codigo'])
        ->map(fn ($p) => [
            'id'     => $p->id,
            'nombre' => $p->nombre,
            'codigo' => $p->codigo
        ]);

    $categorias = Categoria::where('activo', true)
        ->orderBy('nombre')->get();

    return $this->success([
        'promociones' => PromocionResource::collection($promociones),
        'productos'   => $productos,
        'categorias'  => CategoriaResource::collection($categorias),
    ]);
}

Frontend

Los filtros de búsqueda (nombre, tipo, estado activo) se aplican en el cliente sobre el array ya cargado, sin hacer nuevas peticiones al servidor. Las activas siempre aparecen primero.

const promocionesFiltradas = promociones
  .filter(p => {
    const textoOk  = !search     || p.nombre?.toLowerCase().includes(search.toLowerCase());
    const tipoOk   = !filtroTipo || p.tipo_aplicacion === filtroTipo;
    const activoOk = filtroActivo === '' || String(p.activo) === filtroActivo;
    return textoOk && tipoOk && activoOk;
  })
  .sort((a, b) => (b.activo ? 1 : 0) - (a.activo ? 1 : 0)); // activas primero

5
Validación en dos capas antes de llegar a la BD
Zod (frontend) → PromocionRequest.php (backend)
Validación

La validación ocurre en dos momentos: 1) Zod bloquea el submit si el formulario no es válido. 2) PromocionRequest valida de nuevo en el servidor antes de que el controlador toque la base de datos.

// PromocionRequest.php — reglas de validación del servidor
public function rules(): array
{
    $isUpdate = $this->isMethod('PUT') || $this->isMethod('PATCH');

    return [
        'nombre'          => [$isUpdate ? 'sometimes' : 'required', 'string', 'max:150'],
        'tipo_descuento'  => [$isUpdate ? 'sometimes' : 'required', Rule::in(['porcentaje', 'monto_fijo'])],
        'valor_descuento' => [$isUpdate ? 'sometimes' : 'required', 'numeric', 'min:0.01',
            function ($attr, $value, $fail) {
                $tipo = $this->input('tipo_descuento')
                    ?? optional($this->route('promocion'))->tipo_descuento;
                if ($tipo === 'porcentaje' && $value > 100) {
                    $fail('El porcentaje de descuento no puede ser mayor a 100.');
                }
            }
        ],
        'tipo_aplicacion' => [$isUpdate ? 'sometimes' : 'required', Rule::in(['producto', 'categoria'])],
        'producto_id'     => ['nullable', 'integer', Rule::exists('productos', 'id')
                                ->where('activo', true),  /* Closure adicional */],
        'categoria_id'    => ['nullable', 'integer', Rule::exists('categorias', 'id')
                                ->where('activo', true)],
        'fecha_inicio'    => [$isUpdate ? 'sometimes' : 'required', 'date'],
        'fecha_fin'       => ['nullable', 'date', 'after_or_equal:fecha_inicio'],
        'activo'          => ['sometimes', 'boolean'],
    ];
}
Regla condicional inteligente: La Closure de valor_descuento lee el tipo del mismo request (o del modelo existente en edición) y lanza el error solo si es porcentaje mayor a 100. Esto se llama validación cruzada entre campos.
6
El controlador guarda la promoción con FK inteligente
PromocionController::store() — limpia la FK contraria
Backend

Antes de persistir, el controlador anula el campo de FK que no corresponde al tipo seleccionado. Así nunca hay un registro con producto_id Y categoria_id simultáneamente.

public function store(PromocionRequest $request): JsonResponse
{
    $data = $request->validated();
    $data['created_by'] = Auth::id();   // registra quién la creó

    // Limpieza de FK contraria — patrón exclusivo/mutuamente excluyente
    if ($data['tipo_aplicacion'] === 'producto') {
        $data['categoria_id'] = null;   // no aplica a categoría
    } else {
        $data['producto_id'] = null;    // no aplica a producto
    }

    $promocion = Promocion::create($data);

    // Devuelve la promo recién creada con sus relaciones cargadas
    return $this->success(
        new PromocionResource($promocion->load([
            'producto:id,nombre,codigo',
            'categoria:id,nombre'
        ])),
        'Promoción creada exitosamente.',
        201
    );
}
7
El Modelo persiste y activa los Traits automáticos
Promocion.php — Auditable + HasApiCache + SoftDeletes
Base de Datos

Al ejecutar Promocion::create(), Eloquent dispara eventos del modelo. Los Traits suscritos a esos eventos actúan automáticamente sin código adicional.

class Promocion extends Model
{
    use HasFactory, SoftDeletes, Auditable, HasApiCache;

    protected array $cacheModules = ['promociones'];

    protected $casts = [
        'activo'          => 'boolean',
        'valor_descuento' => 'decimal:2',
        'fecha_inicio'    => 'date',
        'fecha_fin'       => 'date',
    ];

    // Scope reutilizable: Promocion::activo()->get()
    public function scopeActivo($query)
    {
        return $query->where('activo', true);
    }

    // Scope vigente: filtra por fecha_inicio <= hoy AND (fecha_fin >= hoy OR null)
    public function scopeVigente($query)
    {
        $hoy = now()->toDateString();
        return $query
            ->where('fecha_inicio', '<=', $hoy)
            ->where(fn ($q) =>
                $q->whereNull('fecha_fin')->orWhere('fecha_fin', '>=', $hoy)
            );
    }

    // Helper del modelo: calcula precio final desde PHP
    public function calcularPrecioFinal(float $precioBase): float
    {
        if ($this->tipo_descuento === 'porcentaje') {
            return max(0, $precioBase - ($precioBase * $this->valor_descuento / 100));
        }
        return max(0, $precioBase - $this->valor_descuento);
    }
}
Traits automáticos: Auditable registra en auditoria_logs quién hizo qué y cuándo. HasApiCache invalida el caché del módulo 'promociones' en cada create/update/delete. SoftDeletes marca deleted_at en vez de borrar físicamente.

Frontend actualiza la lista sin recargar toda la página
recargarPromociones() — solo GET /promociones (no /init)
Frontend

Después de crear/editar/eliminar/toggle, el frontend llama a recargarPromociones() en lugar de fetchAll(). Esto evita re-pedir los catálogos (productos y categorías) que no cambiaron.

// Recarga solo la lista de promociones, no los catálogos
const recargarPromociones = async () => {
  try {
    const res  = await api.get('/promociones');
    const data = res.data?.data ?? res.data;
    const list = Array.isArray(data) ? data : (data?.data ?? []);
    setPromociones(list);
  } catch {
    toast.error('Error al actualizar promociones');
  }
};

// onSubmit: guardar y actualizar lista
const onSubmit = async (data) => {
  // Limpiar FK contraria (igual que el backend — defensa en profundidad)
  if (data.tipo_aplicacion === 'producto') data.categoria_id = null;
  else data.producto_id = null;

  if (editing?.id) {
    await promocionService.update(editing.id, data);  // PUT /promociones/{id}
  } else {
    await promocionService.create(data);              // POST /promociones
  }
  closeModal();
  recargarPromociones();  // actualización parcial
};

toggleActivo: async (id) => {
  const response = await api.patch(`/promociones/${id}/toggle`);
  return response.data;
},

// Backend — PromocionController.php
public function toggleActivo(Promocion $promocion): JsonResponse
{
    $promocion->update(['activo' => !$promocion->activo]);  // invierte booleano
    $estado = $promocion->activo ? 'activada' : 'desactivada';
    return $this->success(new PromocionResource($promocion->fresh()), "Promoción {$estado}.");
}
10
La promoción se aplica automáticamente en el POS
CatalogoProductos.jsx — getPromocionActiva() → calcularPrecioFinal()
Frontend POS

Cuando el POS carga, recibe todas las promociones en el endpoint /pos/init. Al mostrar cada producto, calcula en el cliente si tiene promoción vigente y cuál es el precio con descuento.

// CatalogoProductos.jsx — ¿tiene promo vigente hoy?
function getPromocionActiva(producto, promociones) {
  if (!promociones?.length) return null;
  const hoy = new Date().toISOString().split('T')[0];

  const esVigente = (p) =>
    p.activo &&
    p.fecha_inicio <= hoy &&
    (!p.fecha_fin || p.fecha_fin >= hoy);

  // Prioridad: producto > categoría (operador ??)
  return (
    promociones.find(p =>
      p.tipo_aplicacion === 'producto' &&
      p.producto_id === producto.id &&
      esVigente(p)
    ) ??
    promociones.find(p =>
      p.tipo_aplicacion === 'categoria' &&
      p.categoria_id === producto.categoria_id &&
      esVigente(p)
    ) ??
    null
  );
}

// Calcula el precio final con el descuento de la promo
function calcularPrecioFinal(precioBase, promo) {
  if (!promo) return precioBase;
  if (promo.tipo_descuento === 'porcentaje')
    return Math.max(0, precioBase * (1 - promo.valor_descuento / 100));
  return Math.max(0, precioBase - Number(promo.valor_descuento));
}
Prioridad con ??: Si un producto tiene su propia promo Y su categoría también tiene promo, gana la del producto específico. El operador ?? (nullish coalescing) devuelve el primer find que no sea undefined/null.

4. PromocionResource — Serialización de la Respuesta Backend
¿Qué hace un Resource? Transforma el objeto Eloquent (modelo PHP) en un JSON controlado. Permite elegir exactamente qué campos exponer, cambiar nombres, formatear fechas y manejar relaciones opcionales con whenLoaded(). 
class PromocionResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id'              => $this->id,
            'nombre'          => $this->nombre,
            'tipo_descuento'  => $this->tipo_descuento,
            'valor_descuento' => (float) $this->valor_descuento,  // cast explícito
            'tipo_aplicacion' => $this->tipo_aplicacion,

            // whenLoaded: solo incluye el objeto si fue eager-loaded
            'producto' => $this->whenLoaded('producto', fn () =>
                $this->producto ? [
                    'id'     => $this->producto->id,
                    'nombre' => $this->producto->nombre,
                    'codigo' => $this->producto->codigo,
                ] : null
            ),

            'categoria' => $this->whenLoaded('categoria', fn () =>
                $this->categoria ? [
                    'id'     => $this->categoria->id,
                    'nombre' => $this->categoria->nombre,
                ] : null
            ),

            'fecha_inicio' => $this->fecha_inicio?->format('Y-m-d'),  // null-safe
            'fecha_fin'    => $this->fecha_fin?->format('Y-m-d'),
            'activo'       => $this->activo,
            'created_at'   => $this->created_at?->format('Y-m-d H:i'),
        ];
    }
}

Route Model Binding: El parámetro {promocion} en la URL es resuelto automáticamente por Laravel. Busca en la tabla promociones el registro con ese ID y lo inyecta como objeto Promocion en el método del controlador. Si no existe, responde 404 automáticamente.
6. Preguntas del Docente — Respuestas Detalladas Defensa
¿Cómo evitas que un registro tenga producto_id Y categoria_id al mismo tiempo?
Doble protección: En el frontend, el onSubmit asigna null al campo que no corresponde antes de enviar. En el backend, el store() y update() también limpian la FK contraria. Son dos capas independientes: aunque alguien llame directamente a la API sin pasar por el frontend, el controlador igual limpia el campo.
¿Qué es el scopeVigente y para qué sirve?
Es un Query Scope de Eloquent. Al llamar Promocion::vigente()->get(), agrega automáticamente la condición: fecha_inicio <= hoy AND (fecha_fin IS NULL OR fecha_fin >= hoy). El scope queda encapsulado en el modelo y es reutilizable en cualquier controlador sin repetir la lógica de fechas.
¿Por qué el formulario muestra el selector de Producto o Categoría pero nunca los dos?
El hook watch('tipo_aplicacion') de react-hook-form retorna el valor actual del campo en tiempo real. El JSX usa rendering condicional: {tipoAplicacion === 'producto' && <FormSelect .../>}. Al cambiar el selector, React desmonta el campo anterior y monta el nuevo — sin useState adicional.
¿Cómo se aplica la promoción en el Punto de Venta?
El POS llama a /pos/init y recibe el array promociones. Al renderizar cada producto, getPromocionActiva() busca primero una promo por producto_id y, si no hay, por categoria_id usando el operador ??. Luego calcularPrecioFinal() aplica el descuento. Todo ocurre en el cliente, sin nuevos requests al servidor.
¿Qué pasa con la auditoría cuando se elimina una promoción?
SoftDeletes escribe la fecha en deleted_at en lugar de hacer DELETE físico. El trait Auditable se suscribe al evento deleted del modelo y registra en auditoria_logs: quién eliminó, cuándo, y el estado anterior del registro. El registro sigue en la BD pero Eloquent lo filtra automáticamente.
¿Por qué se usa sometimes en lugar de required en el update?
La regla 'sometimes' le dice al validador "valida este campo solo si está presente en el request". Esto permite hacer un PATCH parcial — actualizar solo el nombre sin enviar todos los campos. $isUpdate = $this->isMethod('PUT') detecta si es creación o edición y cambia la regla dinámicamente.
