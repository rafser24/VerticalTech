1 Descripción General del Sistema

El Sistema de Ventas VerticalTech es una plataforma web de gestión comercial diseñada para pequeñas y medianas empresas. Integra en un solo entorno las operaciones de punto de venta, control de inventario, gestión de compras, administración de clientes y proveedores, sistema de promociones y reportería analítica.

La plataforma está construida bajo una arquitectura de API REST desacoplada: el backend expone endpoints JSON que consume un cliente React de página única (SPA). Esta separación permite escalar, reemplazar o extender cualquiera de las capas de forma independiente.

Objetivos del Sistema

  • Centralizar la operación comercial en una sola interfaz accesible desde el navegador.
  • Controlar el inventario en tiempo real mediante el registro de compras y ventas.
  • Permitir múltiples perfiles de usuario con permisos diferenciados (super-admin, admin, vendedor).
  • Proveer reportería y análisis de ventas para la toma de decisiones gerenciales.
  • Mantener un registro de auditoría completo de todas las acciones realizadas.
  • Garantizar la seguridad mediante autenticación JWT y control de acceso por roles.

2 Arquitectura del Sistema

2.1 Arquitectura General

El sistema sigue el patrón Cliente–Servidor con API REST. El frontend React SPA se comunica exclusivamente con el backend Laravel a través de peticiones HTTP/JSON. El backend no renderiza HTML: toda la presentación es responsabilidad del cliente.

2.2 Backend — Laravel 12

El backend está organizado siguiendo principios de Clean Architecture con separación por dominio de negocio:

app/ Http/ Controllers/Api/ ← Controladores agrupados por dominio Auth/ (AuthenticationController) Catalogos/ (ProductoController, CategoriaController, ClienteController…) Compras/ (CompraController) Ventas/ (VentaController) Pos/ (PosController) Dashboard/ (DashboardController) Usuarios/ (UserController) Configuracion/ (ConfiguracionController) Auditoria/ (AuditoriaController) Middleware/ ← CacheApiResponse Requests/ ← Form Requests con reglas de validación Resources/ ← API Resources (transformación JSON de salida) Models/ ← Eloquent Models organizados por dominio Catalogos/ (Producto, Categoria, Proveedor, Cliente, MetodoPago, Promocion) Ventas/ (Venta, DetalleVenta) Compras/ (Compra, DetalleCompra) Logs/ (AuditoriaLog) Configuracion/ (ConfiguracionEmpresa) Usuario.php Traits/ ← Auditable, HasApiCache database/ migrations/ ← Un archivo por tabla con timestamps routes/ api.php ← Rutas REST protegidas con JWT + middleware de roles

Patrón de Respuesta API Unificada

Todos los controladores heredan de Controller base que provee métodos helper success() y error(). Toda respuesta tiene la misma estructura envolvente:

{ "status": "success" | "error", "message": "Descripción del resultado", "data": { ... } | [ ... ], "meta": { "current_page": 1, "last_page": 5, "total": 47 } }

Sistema de Caché

El middleware CacheApiResponse almacena respuestas GET etiquetadas por módulo. El trait HasApiCache invalida el caché automáticamente en los eventos created, updated y deleted de Eloquent. Los módulos cacheados incluyen: productos, categorias, clientes, proveedores, compras, ventas, dashboard, promociones y pos. El modelo Producto declara $cacheModules = ['productos', 'dashboard'] para invalidar ambos simultáneamente.

2.3 Frontend — React 19

El frontend es una Single Page Application (SPA) construida con React 19 y empaquetada con Vite. El enrutamiento es del lado del cliente mediante React Router v6 con componentes guardián que verifican el rol antes de renderizar cada ruta.

src/ context/ AuthContext.jsx ← JWT + usuario + roles. Persiste en localStorage 'auth-storage' AppContext.jsx ← Estado sidebar (abierto/cerrado) y datos de empresa activa components/ layout/ MainLayout.jsx ← Wrapper de página: sidebar + área de contenido Sidebar.jsx ← Navegación agrupada por sección con control de roles RouteGuard.jsx ← PrivateRoute, AdminRoute, SuperAdminRoute, VendedorRoute, PublicRoute pos/ PosScreen.jsx ← Controlador principal del POS (estado del carrito) CatalogoProductos.jsx ← Grilla de productos con búsqueda y filtros CarritoActivo.jsx ← Líneas del carrito, totales, descuento DrawerVentasEspera.jsx ← Panel lateral de ventas en pausa TicketVenta.jsx ← Comprobante imprimible ui/ DataTable.jsx ← Tabla reutilizable con búsqueda y paginación Modal.jsx ← Modal accesible con trap de foco FormFields.jsx ← FormField, FormInput, FormSelect, FormTextarea ConfirmDialog.jsx ← Diálogo de confirmación de acciones destructivas pages/ ← Una página por módulo del sistema services/ api.js ← Instancia Axios + interceptores JWT + factory crudService() schemas/ index.js ← Esquemas Zod: loginSchema, productSchema, purchaseSchema… utils/ helpers.js ← formatCurrency, formatDate, statusColors, filterData

Gestión de Estado

  • AuthContext (useReducer): token JWT, usuario activo, roles, permisos. Persiste en localStorage bajo la clave auth-storage. Al expirar el token, el interceptor Axios lo limpia y redirige al login.
  • AppContext (useReducer): estado del sidebar (expandido/colapsado) y datos de la empresa activa (nombre, logo, NIT, etc.).
  • Estado local (useState): listas de datos, formularios, modales, flags de carga. Sin librerías de estado global externas.
  • React Hook Form + Zod: formularios no controlados de alto rendimiento con validación schema-first. Evita re-renders innecesarios.

5 Módulos del Sistema

5.1 Autenticación y Sesión

El sistema utiliza autenticación JWT stateless. Al hacer login, el backend valida credenciales contra la tabla usuarios usando el guard api y retorna un token firmado con HS256.

  1. Usuario envía usuario y password a POST /api/auth/login.
  2. Laravel valida con Auth::guard("api")->attempt() mapeando contraseña via getAuthPassword().
  3. JWT firmado retornado junto con el objeto usuario y sus roles/permisos.
  4. Frontend guarda el estado en AuthContext y persiste en localStorage bajo la clave auth-storage.
  5. Cada request incluye el header Authorization: Bearer <token> inyectado por el interceptor Axios.
  6. Al recibir un 401, el interceptor limpia localStorage y redirige a /login.

5.2 Gestión de Usuarios

CRUD completo accesible para admin y super-admin. Incluye creación con asignación de rol, edición, activación/desactivación y eliminación lógica. La contraseña se hashea automáticamente mediante un mutator Eloquent. El super-admin no puede ser eliminado ni editado por un admin.

5.3 Catálogo de Productos

Gestión del inventario de artículos. El stock nunca se modifica desde este módulo: solo aumenta mediante recepciones de compra (incrementarStock()) y disminuye con ventas (decrementarStock()). Si el código no se especifica al crear, se autogenera como PROD-XXXX basado en el ID. Incluye filtros por nombre, código, categoría, proveedor y estado.

5.5 Punto de Venta (POS)

Módulo de cobro diseñado para operación rápida. Al montar la pantalla, un único request a GET /api/pos/init devuelve en paralelo: productos activos con stock, clientes, métodos de pago y promociones vigentes. Evita cuatro round-trips independientes.

  • Catálogo de productos: búsqueda en tiempo real, filtro por categoría, badge de stock disponible.
  • Carrito activo: agregar, quitar y modificar cantidad con validación de existencias en tiempo real.
  • Descuentos: aplicación automática de promociones vigentes y descuento manual porcentual.
  • Ventas en espera: pausar y reanudar ventas sin perder el carrito (DrawerVentasEspera).
  • Ticket de venta: generación de comprobante imprimible con desglose completo de productos, IVA y total.
  • Métodos de pago: efectivo (devuelve vuelto), tarjeta, transferencia (queda pendiente de confirmación).

5.6 Gestión de Ventas

Vista histórica de todas las ventas realizadas. Permite consultar el detalle de cada venta, anularlas (con restricción de rol) y confirmar transferencias bancarias pendientes. Las ventas anuladas no revierten el stock automáticamente.

5.7 Promociones y Descuentos

Motor de descuentos con dos dimensiones de configuración:

%
Tipo de Descuento

Porcentaje: reduce el precio en un % del valor (0–100%).
Monto fijo: resta una cantidad fija en USD al precio.

⊞
Tipo de Aplicación

Producto: aplica solo a un artículo específico.
Categoría: aplica a todos los productos de una categoría.

📅
Vigencia

Fecha de inicio obligatoria. Fecha de fin opcional. El POS solo muestra promociones activas y vigentes.

⚡
Aplicación Automática

El POS aplica automáticamente la promoción más favorable al agregar cada producto al carrito.

5.8 Reportes y Dashboard

El dashboard consume GET /api/dashboard/resumen retornando en un solo request: total ventas, total productos, clientes registrados, alertas de stock bajo y ventas recientes. El módulo de reportes genera: reporte de ventas por período, reporte de compras, top 10 productos más vendidos, top clientes por volumen, y listado de productos con stock bajo o agotado.

5.9 Auditoría del Sistema

El trait Auditable se agrega a todos los modelos de negocio relevantes. Escucha eventos Eloquent (created, updated, deleted) y registra en auditoria_logs: modelo afectado, ID, acción, valores anteriores y nuevos en JSONB, usuario, IP y user-agent. Solo visible para super-admin.

7 Seguridad

7.1 Autenticación JWT

Se utiliza la librería tymon/jwt-auth con el guard api. Los tokens son firmados con algoritmo HS256 usando la clave JWT_SECRET definida en el entorno. El modelo Usuario implementa JWTSubject y agrega claims personalizados (id, nombre, usuario) para evitar consultas adicionales a la BD en cada request.

  • El token se transmite únicamente en el header HTTP, nunca en la URL ni en cookies.
  • Al recibir un 401, el interceptor Axios limpia localStorage y fuerza redireccionamiento al login.
  • El campo contraseña se mapea via getAuthPassword() desde el nombre no estándar contrasena.

7.2 Control de Roles y Permisos

El sistema implementa tres roles jerárquicos mediante Spatie Laravel Permission, todos en el guard api:

RolNivel de AccesoDescripción
super-adminTotalAcceso completo: auditoría, configuración de empresa, gestión de todos los usuarios. No puede ser eliminado ni editado por un admin.
adminAmplioGestiona productos, compras, usuarios (excepto super-admin), reportes, promociones, categorías y proveedores.
vendedorOperativoAcceso al POS, registro y consulta de ventas, catálogo de productos y gestión de clientes.

Las rutas del backend se protegen con middleware role:super-admin|admin o role:super-admin|admin|vendedor. En el frontend, los componentes RouteGuard verifican el rol antes de renderizar y redirigen al dashboard si no tiene permisos.

7.3 Otras Medidas de Seguridad

  • Sanitización de inputs (frontend): el interceptor Axios elimina etiquetas HTML de todos los campos string antes de enviarlos. Protección básica anti-XSS.
  • SoftDeletes universal: ningún registro se elimina físicamente. Preserva integridad referencial e histórica.
  • CORS: configurado en Laravel para aceptar solo el origen del frontend.
  • Form Requests: toda entrada al API pasa por una clase de validación específica (ProductoRequest, CompraRequest, etc.) con reglas de tipo, tamaño y unicidad.
  • Columnas computed stored: subtotales calculados por PostgreSQL, no por la aplicación. Imposible manipular desde el cliente.
  • Hash de contraseña: bcrypt vía mutator Eloquent setContrasenaAttribute(). La clave en texto plano nunca se almacena.
  • Protección super-admin: el UserController bloquea explícitamente la edición y eliminación de cuentas super-admin por parte de administradores regulares.
  • withCredentials: la instancia Axios incluye withCredentials: true para cookies de sesión CSRF en rutas web.
8 Patrones y Decisiones de Diseño

Factory CRUD Genérico (Frontend)

La función crudService(endpoint) en services/api.js genera automáticamente los métodos getAll, getById, create, update, remove y toggle para cualquier endpoint. Todos los servicios de entidades (productService, clientService, userService…) se crean con una sola línea, eliminando duplicación de código Axios.

const crudService = (endpoint) => ({ getAll: (params) => api.get(endpoint, { params }), getById: (id) => api.get(`${endpoint}/${id}`), create: (data) => api.post(endpoint, data), update: (id, data) => api.put(`${endpoint}/${id}`, data), remove: (id) => api.delete(`${endpoint}/${id}`), toggle: (id) => api.patch(`${endpoint}/${id}/toggle`), }); export const productService = crudService('/productos'); export const userService = crudService('/usuarios'); // ... etc.

Init Endpoint Pattern (Backend)

En lugar de hacer N peticiones paralelas al montar un módulo, cada pantalla llama a un único endpoint /modulo/init que devuelve todos los catálogos necesarios. Reduce el número de round-trips, permite un caché unificado por módulo y hace que el middleware de caché sea más eficiente.

React Context + useReducer (sin Redux/Zustand)

El estado global se maneja con la API nativa de React. AuthContext gestiona la sesión JWT y AppContext el estado de la UI. El sistema fue migrado exitosamente desde Zustand, eliminando una dependencia externa sin perder funcionalidad. Las páginas usan estado local (useState) para datos que no necesitan compartirse entre componentes.

Auditable Trait (Backend)

Un trait Eloquent reutilizable que escucha los eventos del modelo (created, updated, deleted) y registra automáticamente en auditoria_logs. Se agrega con un simple use Auditable; en cualquier modelo, sin modificar el controlador ni los métodos de negocio.

HasApiCache Trait (Backend)

Trait que invalida el caché de los módulos relacionados al modificar cualquier entidad. Los módulos a invalidar se declaran en la propiedad $cacheModules. Por ejemplo, el modelo Producto invalida tanto el caché de "productos" como el de "dashboard" simultáneamente:

class Producto extends Model { use HasApiCache; protected array $cacheModules = ['productos', 'dashboard']; // ... }

RouteGuard Components (Frontend)

Componentes React que envuelven rutas y verifican el rol antes de renderizar. Centralizan la lógica de autorización en el enrutador en lugar de dispersarla en cada página. Si el usuario no tiene el rol requerido, redirige al dashboard sin mostrar contenido protegido.

// En App.jsx — el componente decide si renderiza o redirige <Route path="/auditoria" element={ <SuperAdminRoute><AuditoriaPage /></SuperAdminRoute> } />

Stock Inmutable desde la UI

El campo stock no aparece en el formulario de productos y el backend lo ignora explícitamente en store() y update(). El único movimiento válido es mediante recepciones de compra (incrementarStock) y ventas (decrementarStock). Ambos métodos usan DB::raw() directo para mayor eficiencia que el increment() estándar de Eloquent.

Columnas Computed Stored (PostgreSQL)

Los subtotales en detalle_venta y detalle_compra son columnas storedAs calculadas por el motor de base de datos: (cantidad * precio_unitario) - descuento. Esto garantiza consistencia matemática independientemente de qué capa crea el registro, y permite indexar la columna para reportes rápidos.

Soft Delete Universal

Todas las entidades de negocio usan SoftDeletes de Eloquent. Esto garantiza que los registros históricos (ventas, compras, auditoría) nunca pierdan sus relaciones por la eliminación de un cliente, producto o proveedor. Las migraciones incluyen el índice sobre deleted_at para que Eloquent filtre eficientemente con WHERE deleted_at IS NULL.

9.2 Instalación del Backend

  1. Clonar el repositorio y navegar a /backend.
  2. Copiar .env.example a .env y configurar las variables de base de datos.
  3. Ejecutar composer install para instalar dependencias PHP.
  4. Ejecutar php artisan key:generate para generar la clave de aplicación.
  5. Ejecutar php artisan jwt:secret para generar la clave de firma JWT.
  6. Crear la base de datos en PostgreSQL y configurar DB_* en .env.
  7. Ejecutar php artisan migrate --seed para crear tablas y datos iniciales (roles, permisos, super-admin).
  8. Ejecutar php artisan storage:link para enlazar almacenamiento público (logos, fotos).
  9. Levantar servidor: php artisan serve (desarrollo) o configurar Nginx + PHP-FPM (producción).

9.4 Instalación del Frontend

  1. Navegar a /frontend.
  2. Copiar .env.example a .env y configurar VITE_API_URL con la URL del backend.
  3. Ejecutar npm install para instalar dependencias JavaScript.
  4. Desarrollo: npm run dev levanta el servidor Vite con HMR en el puerto 5173.
  5. Producción: npm run build genera la carpeta /dist para servir con Nginx o Apache.
⚠ Nota de producción: configurar Nginx para que todas las rutas no encontradas devuelvan index.html (requerido para SPA con enrutamiento del lado del cliente). Ejemplo: try_files $uri $uri/ /index.html;

9.5 Configuración Inicial del Sistema

El seeder de base de datos crea automáticamente:

  • Los tres roles del sistema: super-admin, admin, vendedor en el guard api.
  • Un usuario super-admin inicial con credenciales configurables en el seeder.
  • Los métodos de pago estándar: efectivo, tarjeta de crédito/débito, transferencia bancaria, cheque.
  • Una categoría por defecto para productos sin clasificar.
