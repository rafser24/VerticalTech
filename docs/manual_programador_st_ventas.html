1. Visión General del Proyecto

Descripción, objetivos y alcance del sistema

ST Ventas es un sistema de gestión de punto de venta (POS) y administración de inventario con arquitectura desacoplada: API REST en Laravel 12 (PHP 8.2) y SPA en React 19. Permite registrar ventas, gestionar inventario, controlar compras a proveedores y generar reportes, con autenticación JWT, control de acceso por roles y auditoría automática de todos los cambios en la base de datos.

Módulos Funcionales

  • Dashboard — KPIs, gráficos, resumen ejecutivo
  • POS — Punto de venta con carrito, descuentos y tickets PDF
  • Ventas — Historial, filtros, anulaciones, transferencias pendientes
  • Compras — Flujo de estados: pendiente → confirmada → recibida
  • Productos / Categorías / Proveedores — Catálogos
  • Clientes — Directorio con historial de compras
  • Usuarios — ABM con roles y permisos
  • Reportes — Ventas, compras, top productos, top clientes, stock bajo
  • Auditoría — Log completo de cambios (solo super-admin)
  • Configuración — Datos de empresa y perfil (solo super-admin)

Características Técnicas Destacadas

  • Init Endpoint Pattern — 1 HTTP carga N catálogos
  • Caché Redis versionado — invalidación automática por modelo
  • Trait Auditable — log CUD automático en todos los modelos
  • JWT + Rate Limiter — 5 intentos por IP por minuto
  • Transacciones BD — ventas y compras son atómicas
  • storedAs PostgreSQL — subtotal calculado en BD
  • Sanitización XSS — interceptor Axios limpia HTML antes de POST
  • SoftDeletes — usuarios y productos nunca se borran realmente

API Resources — Transformación JSON

Cada modelo tiene su Resource que controla qué campos se exponen. Los campos $hidden del modelo (contrasena, remember_token) nunca llegan al Resource. Se usan relaciones lazy con whenLoaded() para evitar N+1.

// Ejemplo: ProductoResource
return [
    'id'           => $this->id,
    'codigo'       => $this->codigo,
    'nombre'       => $this->nombre,

    'activo'       => $this->activo,
    'categoria'    => new CategoriaResource($this->whenLoaded('categoria')),

Modelo Usuario — Interfaz JWTSubject

class Usuario extends Authenticatable implements JWTSubject {
    // Nuestro campo se llama 'contrasena', no 'password':
    public function getAuthPassword(): string { return $this->contrasena; }

    // Claims extras dentro del payload JWT:
    public function getJWTCustomClaims(): array {
        return ['id' => $this->id, 'nombre' => $this->nombre_completo, 'usuario' => $this->usuario];
    }
}

9. Sistema de Caché Redis

CacheApiResponse middleware + HasApiCache trait — invalidación versionada

Arquitectura del Sistema de Caché

CacheApiResponse Middleware

Intercepta todos los GET y construye una clave versionada:

api_resp:{modulo}:v{version}:{sha256(URL)}

Si existe en Redis → X-Cache: HIT sin tocar la BD.
Si no → procesa, guarda, X-Cache: MISS.

HasApiCache Trait

Adjunto a modelos. Al saved() o deleted():

Cache::increment("cache_ver:{modulo}");

La versión cambia → claves antiguas quedan huérfanas → expiran por TTL solas.

TTL por Módulo

MóduloTTLRazón
metodos-pago1800s (30 min)Nunca cambia en operación normal
categorias, proveedores600s (10 min)Cambios esporádicos
promociones, productos300s (5 min)Gestión diaria
pos120s (2 min)Init combina 4 catálogos — stock cambia con cada venta
clientes, compras120s (2 min)Operaciones frecuentes
ventas, dashboard60s (1 min)Alta frecuencia de cambio
auth, auditoria, usersSKIPNunca se cachean — datos sensibles/siempre frescos

Uso del Trait en Modelos

// Invalidación simple (usa nombre de tabla por defecto):
class Categoria extends Model { use HasApiCache; }

// Invalidación múltiple (Producto invalida también el dashboard):
class Producto extends Model {
    use HasApiCache;
    protected array $cacheModules = ['productos', 'dashboard'];
}

// Invalidación manual (cuando decrement() no dispara eventos Eloquent):
$this->decrement('stock', $cantidad);
$this->invalidateCache(['productos', 'dashboard']);

10. Sistema de Auditoría

Trait Auditable + tabla auditoria_logs — log automático de todos los cambios

// Adjuntar al modelo — registra CUD automáticamente:
class Venta extends Model { use Auditable, HasApiCache; }

// Eventos registrados por el trait boot:
static::created  → accion='created',  valores_nuevos=toArray()
static::updated  → accion='updated',  valores_anteriores=getOriginal(), valores_nuevos=getChanges()
static::deleted  → accion='deleted',  valores_anteriores=toArray()

// Los campos $hidden del modelo se excluyen automáticamente del log.
// Si la auditoría falla, la operación principal NO se interrumpe (try/catch silencioso).

Lectura del Token Fuera de React

// api.js — interceptores Axios no pueden usar useContext():
function getToken() {
  const raw = localStorage.getItem('auth-storage');
  const data = JSON.parse(raw);
  // Compat. con formato Zustand antiguo: { state: { token }, version }
  return (data.state ?? data)?.token ?? null;
}

16. Patrones y Decisiones Técnicas

Razones detrás de las decisiones de diseño

PatrónDecisión y Razón
Init Endpoint Pattern1 HTTP carga N catálogos. Con JWT + Redis cada request extra cuesta ~5-20ms de overhead. En conexiones lentas la percepción de velocidad mejora notablemente.
storedAs en subtotalPostgreSQL garantiza que subtotal = (cantidad * precio_unitario) - descuento siempre. No depende de PHP. Si alguien actualiza via SQL raw, el valor sigue correcto.
Caché versionada (no flush)Incrementar un entero es O(1). Borrar claves con SCAN es O(N). Las claves huérfanas expiran por TTL sin intervención manual.
Trait en lugar de BaseModelComposición > herencia. No todos los modelos necesitan caché o auditoría. Cada uno declara sus módulos independientemente.
Context + useReducerAuth cambia 2-3 veces por sesión (login/logout/updateUser). No justifica dependencia externa. El reducer hace el código más explícito y testeable.
useState local en POSEl carrito es efímero. Context global causaría re-renders en todos los consumidores del AuthContext con cada item agregado.
getToken() leyendo localStorageLos interceptores de Axios se ejecutan fuera del árbol React. No pueden llamar a useContext(). Es la única solución correcta sin singleton de estado externo.
SoftDeletes en usuarios/productosUn usuario "eliminado" sigue referenciado en ventas históricas. SoftDelete preserva la integridad referencial y el historial.
Rate Limiter en login5 intentos/IP/min sin CAPTCHA. El decay es por IP (no por usuario) para evitar DoS contra cuentas específicas — un atacante no puede bloquear a un usuario.
Solo PostgreSQLSe usan ILIKE, jsonb, storedAs con expresiones, NOW() - INTERVAL '12 months'. Migrar a MySQL requeriría reescribir todas estas queries.
Número de venta correlativoVTA-YYYY-NNNNNN. Se usa COUNT sin lockForUpdate porque PostgreSQL no permite FOR UPDATE con funciones de agregación. Para producción de alto volumen considerar SEQUENCE nativa.

  • ✅ APP_DEBUG=false — nunca exponer stack traces en producción
  • ✅ JWT_SECRET único por entorno — regenerar con php artisan jwt:secret

export default function AlmacenesPage() {
