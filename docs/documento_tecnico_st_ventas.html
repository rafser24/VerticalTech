Resumen Ejecutivo

st_ventas es una plataforma web de punto de venta (POS) y gestión empresarial (ERP) diseñada para negocios de retail y comercio en general. Permite controlar el ciclo completo de operaciones comerciales: desde la gestión del catálogo de productos y proveedores, pasando por el registro de compras (entrada de inventario), la venta directa en mostrador (POS), hasta la generación de reportes gerenciales y auditoría de todas las acciones del sistema.

✅
El sistema fue construido con un enfoque en rendimiento (patrón init endpoint + caché Redis), seguridad (JWT stateless + RBAC granular) y mantenibilidad (separación estricta de capas, validaciones duales).

Capacidades principales

ÁreaDescripción
POS / CajaVenta rápida con búsqueda de productos, carrito dinámico, métodos de pago, descuentos e impuestos. Emite comprobante en pantalla.
InventarioCatálogo de productos con control de stock. El stock solo se mueve por compras y ventas (no edición manual), preservando el historial de auditoría.
ComprasRegistro de entradas de mercancía por proveedor. Actualiza automáticamente el stock y registra el costo promedio.
ClientesBase de datos de clientes con historial de compras y saldo pendiente.
UsuariosGestión de cuentas con roles (super-admin, admin, vendedor). Protección de cuentas privilegiadas.
ReportesDashboard con ventas por período, top productos, top clientes y alertas de stock bajo.
AuditoríaLog inmutable de todas las acciones sensibles: quién, qué, cuándo y desde qué IP.
ConfiguraciónDatos de la empresa, logo, información fiscal. Exclusivo super-admin.

Arquitectura del Sistema

El sistema sigue una arquitectura cliente-servidor desacoplada. El backend expone una API REST con respuestas JSON estandarizadas; el frontend es una SPA (Single Page Application) que consume esa API de forma exclusiva. No hay renderizado server-side: toda la lógica de UI corre en el navegador.

Flujo de una solicitud típica

// 1. Usuario interactúa con la UI
React Component  ──[evento]──▶  Handler (useState / useCallback)
                                        │
                                        ▼
// 2. Servicio Axios agrega el token JWT al header
api.js (interceptor)  ──[Authorization: Bearer <token>]──▶  Laravel API

// 3. Laravel procesa la petición en capas
Router (api.php)
  │── Middleware: auth:api  (verifica JWT)
  │── Middleware: role:xxx  (verifica permisos Spatie)

  ▼
FormRequest ──[valida body]──▶ Controller ──[lógica]──▶ Model (Eloquent)

{ "status": true, "message": "...", "data": {...}, "pagination": {...} }

Módulo POS — Flujo detallado

El POS es el corazón operativo del sistema. Su flujo interno es el siguiente:

// 1. Carga inicial — un único request consolida todo
GET /api/pos/init
→ { productos[], metodos_pago[], config_empresa }

// 2. El cajero construye el carrito en memoria (Zustand o useState local)
carrito = [{ producto_id, nombre, precio, cantidad, subtotal }]

// 3. Al confirmar la venta
POST /api/pos/venta
{
  cliente_id: 5,          // null = "Cliente General"
  metodo_pago_id: 1,
  descuento: 0,
  impuesto: 0,
  items: [
    { producto_id: 12, cantidad: 2, precio_unitario: 25.00, descuento: 0 }
  ]
}

// 4. Backend ejecuta en una transacción atómica:
//    a) Crea Venta + DetalleVenta
//    b) Descuenta stock: productos.stock -= cantidad
//    c) Registra en auditoría
//    d) Invalida caché del módulo productos
→ { venta_id, numero_venta, total, ... }

Módulo Compras — Regla de negocio del stock

⚠️
El stock de productos solo se mueve en dos momentos: cuando se registra una compra (entrada) y cuando se realiza una venta (salida). El formulario de Productos no expone el campo stock porque editarlo directamente rompería el historial de auditoría y desincronizaría el inventario. El backend lo ignora en store() y update().

Seguridad y Control de Acceso

Autenticación — JWT Stateless

Se usa tymon/jwt-auth 2.2 con tokens firmados (HS256). El token se emite al hacer login y el cliente lo almacena en localStorage (gestionado por Zustand's authStore). Cada request privado envía el header Authorization: Bearer <token>. El servidor no mantiene sesiones — cada verificación es autocontenida en el token. 

// api.js — interceptor de request (frontend)
api.interceptors.request.use(config => {
  const token = useAuthStore.getState().token;
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// Interceptor de respuesta — limpia sesión si el token expiró
api.interceptors.response.use(null, error => {
  if (error.response?.status === 401) {
    useAuthStore.getState().logout();
    window.location.href = '/login';
  }
  return Promise.reject(error);
});

Autorización — RBAC con Spatie

Los roles disponibles son tres: super-admin, admin y vendedor. Se aplican a nivel de middleware en las rutas del backend. 

// routes/api.php — ejemplo de protección por rol
Route::middleware(['auth:api', 'role:super-admin'])->group(function() {
    Route::apiResource('auditoria', AuditoriaController::class)->only(['index']);
    Route::get('/configuracion/empresa', [ConfiguracionController::class, 'getEmpresa']);
    Route::post('/configuracion/empresa', [ConfiguracionController::class, 'updateEmpresa']);
});

Protección de cuentas privilegiadas (Super Admin)

Un administrador no puede editar, eliminar ni activar/desactivar la cuenta de un super-admin. Esta regla se aplica en dos capas independientes:

CapaMecanismoResultado si viola
Backend Guard en UserController — comprueba hasRole('super-admin') en el usuario objetivo HTTP 403 con mensaje claro
Frontend UsersPage oculta los botones de acción cuando row.rol === 'super-admin' y el actor no es super-admin Se muestra "—" en lugar de los botones

Guards de ruta en el frontend

// App.jsx — protección declarativa por rol
<Route path="/auditoria"
  element={<SuperAdminRoute><AuditoriaPage /></SuperAdminRoute>}
/>
<Route path="/dashboard"
  element={<AdminRoute><DashboardPage /></AdminRoute>}
/>

Saneado de entradas HTML

ℹ️
El interceptor de request en Axios recorre recursivamente el body y convierte los campos string a texto plano (DOMParser + textContent) antes de enviarlos al servidor. Esto previene inyección de HTML/XSS desde el cliente incluso si el usuario escapa la validación del formulario.

Patrón Init Endpoint

Muchos módulos necesitan varios catálogos al abrirse: por ejemplo, el formulario de Productos necesita la lista de productos, las categorías y los proveedores. En lugar de hacer tres requests separados (cada uno con su validación JWT, conexión a DB, etc.), se consolida todo en un único endpoint /modulo/init.

MóduloEndpoint initDatos que consolida
ProductosGET /productos/initproductos, categorías, proveedores
ComprasGET /compras/initcompras, proveedores, productos
POSGET /pos/initproductos activos, métodos de pago, config empresa
DashboardGET /dashboard/initmétricas del día, ventas recientes, stock bajo
ReportesGET /dashboard/reporte-completoresumen, ventas por período, top productos/clientes, stock bajo

Implementación típica — backend

// ProductoController.php
public function init(Request $request)
{
    return $this->success([
        'productos'   => Producto::with('categoria')->orderBy('nombre')->get(),
        'categorias'  => Categoria::orderBy('nombre')->get(),
        'proveedores' => Proveedor::where('activo', true)->orderBy('nombre')->get(),
    ], 'Init de productos');
}

Implementación típica — frontend

// ProductsPage.jsx — carga inicial
useEffect(() => {
  const loadData = async () => {
    try {
      const res  = await api.get('/productos/init');
      const data = res.data?.data ?? {};
      // Un solo round-trip devuelve todo lo que necesita el módulo
      setProducts(data.productos ?? []);
      setCategories(data.categorias ?? []);
      setSuppliers(data.proveedores ?? []);
    } catch {

  };
  loadData();
}, []);

Sistema de Caché

Las respuestas GET de la API se cachean en Redis usando el middleware CacheApiResponse. El mecanismo es automático: si existe una entrada válida en Redis, se devuelve directamente sin tocar la base de datos. Cuando un modelo cambia (creación, actualización o eliminación), el trait HasApiCache incrementa un contador de versión en Redis, invalidando automáticamente el caché de ese módulo.

Flujo de lectura con caché

// CacheApiResponse.php
public function handle($request, Closure $next)
{
    if ($request->method() !== 'GET') return $next($request);

    $modulo  = $this->resolveModulo($request);
    $version = Cache::get("cache_ver:{$modulo}", 0);
    $cacheKey = "api:{$modulo}:v{$version}:" . md5($request->fullUrl());

    if (Cache::has($cacheKey)) {
        return response()->json(Cache::get($cacheKey));
    }

    $response = $next($request);

    if ($response->status() === 200) {
        Cache::put($cacheKey, $response->getData(), now()->addMinutes(30));
    }

    return $response;
}

Invalidación automática — trait HasApiCache

// HasApiCache.php — se agrega a cada Model que necesite caché
protected static function bootHasApiCache(): void
{
    static::saved(fn() => Cache::increment("cache_ver:" . static::$cacheModule));
    static::deleted(fn() => Cache::increment("cache_ver:" . static::$cacheModule));
}
ℹ️
Al incrementar el número de versión, todas las claves antiguas de ese módulo quedan "huérfanas" en Redis y expiran de forma natural. No hay necesidad de borrar claves específicas — la versión actúa como un namespace rotativo.

Validación y Formularios

El sistema implementa validación en dos capas independientes. Aunque parezca redundante, es necesario: la validación en el cliente mejora la experiencia de usuario (feedback inmediato sin round-trip); la validación en el servidor es la verdadera línea de defensa (el cliente nunca es de confianza).

CapaTecnologíaCuándo actúaObjetivo
Cliente React Hook Form + Zod Al cambiar el campo (onChange) y al intentar enviar UX: mensajes de error instantáneos, deshabilita submit si hay errores
Servidor Laravel FormRequest Antes de llegar al controlador Seguridad: valida tipos, existencia en DB (exists:), unicidad (unique:)

Ejemplo — esquema Zod (cliente)

// schemas/index.js
export const productSchema = z.object({
  nombre:       z.string().min(2, "Mínimo 2 caracteres"),
  precio_venta: z.coerce.number().positive("Debe ser mayor a 0"),
  categoria_id: z.coerce.number().int().positive("Seleccionar categoría"),
  stock_minimo: z.coerce.number().int().min(0).optional(),
  proveedor_id: z.coerce.number().int().positive().optional().nullable(),
  unidad:       z.enum(['unidad', 'caja', 'kg', 'litro', 'metro']).optional(),
});

Ejemplo — FormRequest (servidor)

// Requests/Productos/ProductoStoreRequest.php
public function rules(): array
{
    return [
        'nombre'       => ['required', 'string', 'max:150'],
        'precio_venta' => ['required', 'numeric', 'min:0'],
        'categoria_id' => ['required', 'integer', 'exists:categorias,id'],
        'proveedor_id' => ['nullable', 'integer', 'exists:proveedores,id'],
        'codigo'       => ['nullable', 'string', 'unique:productos,codigo'],
    ];
}

Auditoría

El sistema mantiene un log inmutable de todas las acciones sensibles. El módulo de Auditoría es exclusivo del super-admin y no puede ser modificado ni eliminado por ningún usuario — es append-only a nivel de lógica de negocio.

Estructura del registro

CampoTipoDescripción
idintegerIdentificador único
usuario_idintegerFK al usuario que realizó la acción
accionstringVerbo de la acción: CREATE, UPDATE, DELETE, LOGIN, LOGOUT, etc.
modulostringMódulo afectado: productos, ventas, usuarios, etc.
entidad_idinteger|nullID del recurso afectado
descripciontextDetalle legible de la operación
ipstringIP del cliente al momento de la acción
created_attimestampFecha y hora exacta (inmutable)

Eventos auditados

Se auditan automáticamente: login/logout de usuarios, creación/edición/eliminación de productos, registro de ventas, registro de compras, cambios en datos de empresa, creación/modificación de usuarios y cambios de rol.

🔒
El endpoint GET /api/auditoria está protegido con middleware role:super-admin. No existe endpoint de eliminación — los registros de auditoría no se pueden borrar por diseño.

Decisiones de Diseño

DecisiónAlternativa consideradaRazón de elección
JWT stateless Sanctum con sesiones / cookies La API es consumida por un SPA desacoplado. JWT elimina la necesidad de CSRF y funciona con cualquier cliente HTTP.
Zustand en lugar de Redux Redux Toolkit, Recoil Estado mínimo (solo auth y UI global). Zustand tiene cero boilerplate y se integra nativamente con React 19 hooks.
Init endpoint en lugar de Promise.allSettled Múltiples requests paralelos Reduce validaciones JWT, conexiones a DB y complejidad de estados de error en el frontend. Un solo punto de fallo es más fácil de manejar.
Stock inmutable desde la UI de productos Edición directa del campo stock Preserva el historial de auditoría. El stock es un valor calculado por las transacciones (compras y ventas), no un dato editable arbitrariamente.
PostgreSQL en lugar de MySQL MySQL 8, SQLite Soporte nativo de ilike (búsqueda case-insensitive sin función), mejor soporte de transacciones concurrentes, JSONB para metadatos futuros.
Caché por versión (counter) en Redis Invalidación por clave específica, TTL fijo Al rotar el número de versión no es necesario conocer exactamente qué claves existen. Las entradas viejas expiran naturalmente sin un proceso de limpieza.
Validación dual (Zod + FormRequest) Solo servidor, solo cliente Cliente: UX inmediata. Servidor: seguridad real. Son responsabilidades distintas y no se excluyen.
Defense in depth para super-admin Solo guard de frontend o solo backend El frontend puede ser manipulado. El backend es la fuente de verdad. Ambas capas trabajan de forma independiente.

Glosario

TérminoDefinición
JWTJSON Web Token. Token firmado criptográficamente que contiene los datos del usuario y sus roles. No requiere sesión en el servidor.
RBACRole-Based Access Control. Sistema de permisos donde el acceso se otorga según el rol del usuario (super-admin, admin, vendedor).
SPASingle Page Application. La UI carga una vez y navega sin recargar el navegador, intercambiando solo datos JSON con el servidor.
Init EndpointEndpoint consolidado que retorna todos los datasets necesarios para inicializar un módulo en una sola petición HTTP.
Eager LoadingTécnica de Eloquent (with()) que carga las relaciones en la misma consulta SQL para evitar el problema N+1.
N+1 ProblemAnti-patrón donde se ejecuta 1 consulta para obtener N registros y luego N consultas adicionales para sus relaciones.
