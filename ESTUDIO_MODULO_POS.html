Mapa de componentes del POS

Antes de entrar al código, es importante entender quién hace qué. El módulo POS tiene 5 archivos en el frontend y 2 controladores en el backend:

🟠 Frontend — React
PosScreen.jsx
Cerebro del POS. Guarda todo el estado (carrito, cliente, etc.) y pasa funciones hacia abajo como props.
CatalogoProductos.jsx
Grilla de productos. Filtra en tiempo real. Calcula promociones. Llama a agregarProducto().
CarritoActivo.jsx
Lista de ítems, totales, cobro y pausa (transferencia).
DrawerVentasEspera.jsx
Panel lateral de ventas pendientes de transferencia.
TicketVenta.jsx
Comprobante imprimible que aparece al completar la venta.
🔵 Backend — Laravel
PosController@init
Devuelve en UN SOLO request: productos, clientes, métodos de pago y promociones vigentes.
VentaController@store
Registra la venta completa: valida, verifica stock, crea la venta y descuenta unidades.
VentaController@storePendiente
Registra venta en espera de transferencia. Estado = pendiente.
VentaController@confirmarTransferencia
Cambia estado pendiente → completada.
VentaRequest
Valida todos los campos antes de llegar al controlador (Form Request).
🟢 Base de Datos
Tabla: ventas
Cabecera de la transacción: número, cliente, método de pago, totales, estado.
Tabla: detalle_venta
Líneas de la venta (producto, cantidad, precio). subtotal es columna COMPUTED STORED.
Tabla: productos
El campo stock se descuenta con UPDATE directo usando DB::raw("GREATEST(stock - N, 0)").
DB::transaction()
Garantiza que venta + detalles + stock se crean juntos o ninguno. Si algo falla: ROLLBACK.
🎯 Frase clave para el docente "El estado del carrito vive en PosScreen mediante useState y se comparte hacia abajo con props. No usé ninguna librería de estado global como Redux o Zustand — solo React puro. Esto hace el código más fácil de entender y depurar."

public function init(): JsonResponse
{
    // 1. Solo productos activos Y con existencias. Con Eager Load de categoría
    $productos = Producto::with('categoria')
        ->where('activo', true)
        ->where('stock', '>', 0)   // ← no enviar productos sin stock al POS
        ->orderBy('nombre')
        ->get();

    // 2. Clientes y métodos de pago activos
    $clientes    = Cliente::where('activo', true)->orderBy('nombre')->get();
    $metodosPago = MetodoPago::where('activo', true)->get();

    // 3. Solo promociones vigentes HOY (activo + rango de fechas)
    $hoy = now()->toDateString();
    $promociones = Promocion::where('activo', true)
        ->whereDate('fecha_inicio', '<=', $hoy)
        ->where(fn($q) =>
            $q->whereNull('fecha_fin')              // promo sin fecha fin = indefinida
              ->orWhereDate('fecha_fin', '>=', $hoy)  // o fecha fin mayor a hoy
        )->get();

    // 4. Respuesta unificada (el método success() viene del Controller base)
    return $this->success([
        'productos'    => ProductoResource::collection($productos),
        'clientes'     => ClienteResource::collection($clientes),
        'metodos_pago' => MetodoPagoResource::collection($metodosPago),
        'promociones'  => PromocionResource::collection($promociones),
    ]);
}
💡 ¿Por qué un solo endpoint /pos/init? "Diseñé un único endpoint que devuelve todos los catálogos juntos. Así el POS solo hace 1 validación JWT, 1 verificación de rol y 1 consulta al servidor en lugar de 4. Además, el middleware de caché guarda esa respuesta completa, haciendo el segundo acceso instantáneo."

Función getPromocionActiva() — línea 9
Busca si el producto tiene promo propia; si no, busca promo de su categoría.
function getPromocionActiva(producto, promociones) {
  const hoy = new Date().toISOString().split('T')[0]; // formato 'YYYY-MM-DD'

  // Función auxiliar que verifica si la promo está vigente hoy
  const esVigente = (p) =>
    p.activo
    && p.fecha_inicio <= hoy
    && (!p.fecha_fin || p.fecha_fin >= hoy);

  return (
    // Primero: promo específica para ESE producto
    promociones.find(p =>
      p.tipo_aplicacion === 'producto'
      && p.producto_id  === producto.id
      && esVigente(p)
    ) ??  // ← si no encuentra (null), prueba la siguiente

    // Si no hay: promo para su CATEGORÍA
    promociones.find(p =>
      p.tipo_aplicacion === 'categoria'
      && p.categoria_id === producto.categoria_id
      && esVigente(p)
    ) ??
    null  // si ninguna aplica, retorna null
  );
}

// Calcula el precio final según el tipo de descuento
function calcularPrecioFinal(precioBase, promo) {
  if (!promo) return precioBase;  // sin promo: precio normal
  if (promo.tipo_descuento === 'porcentaje')
    return Math.max(0, precioBase * (1 - promo.valor_descuento / 100));
  return Math.max(0, precioBase - Number(promo.valor_descuento));  // monto fijo
}
💡 Clave del operador ?? El operador "nullish coalescing" ?? evalúa la expresión de la derecha solo si la izquierda es null o undefined. Permite encadenar búsquedas de prioridad sin if/else anidados.

PASO 3 — Gestión del carrito: funciones en PosScreen.jsx

🎯 Concepto clave: ¿Por qué el estado está en PosScreen y no en CarritoActivo? Porque CatalogoProductos y CarritoActivo necesitan compartir el mismo estado. Si el estado viviera en CarritoActivo, el catálogo no sabría cuántas unidades hay en el carrito (para mostrar el badge "2 en carrito"). Al tenerlo arriba en PosScreen, ambos hijos reciben los datos como props.
FE
Funciones del carrito — PosScreen.jsx líneas 66-113
Todas envueltas en useCallback para no recrearse en cada render.
// useCallback memoriza la función — solo se recrea si cambian sus dependencias
const agregarProducto = useCallback((producto) => {
  setCarritoActual(prev => {          // prev = estado anterior del carrito
    const existe = prev.find(p => p.id === producto.id);
    if (existe) {
      // Producto YA está: incrementa cantidad (sin pasar del stock disponible)
      return prev.map(p =>
        p.id === producto.id && p.cantidad < p.stock
          ? { ...p, cantidad: p.cantidad + 1 }
          : p
      );
    }
    // Producto NUEVO: lo agrega con cantidad 1
    return [...prev, { ...producto, cantidad: 1 }];
  });
}, []);

const cambiarCantidad = useCallback((productoId, cantidad) => {
  setCarritoActual(prev =>
    prev.map(p =>
      p.id === productoId
        ? { ...p, cantidad: Math.max(1, Math.min(cantidad, p.stock)) }
        // Math.max(1,...) → nunca menos de 1
        // Math.min(..., p.stock) → nunca más que el stock disponible
        : p
    )
  );
}, []);

const quitarProducto = useCallback((productoId) => {
  setCarritoActual(prev => prev.filter(p => p.id !== productoId));
}, []);

const limpiarCarrito = useCallback(() => {
  setCarritoActual([]); setClienteActual(null);
  setMetodoPagoId(null);  setDescuento(0);  setNotas('');
}, []);
💡 Patrón funcional de setState setCarritoActual(prev => ...) recibe el estado anterior como parámetro. Esto evita el bug clásico de closures donde la función capturaría un valor desactualizado. Es la forma correcta cuando el nuevo estado depende del anterior.

DB::transaction() — el corazón del módulo (líneas 77-125)
Todo ocurre dentro de una transacción PostgreSQL. Si algo falla: ROLLBACK.
$venta = DB::transaction(function () use ($data) {

    // 1. CALCULAR TOTALES
    $subtotal  = 0;
    $descuento = (float) ($data['descuento'] ?? 0);

    foreach ($data['items'] as &$item) {          // & = referencia (modifica el array)
        $item['descuento'] = (float) ($item['descuento'] ?? 0);
        $lineSubtotal      = ($item['cantidad'] * $item['precio_unitario']) - $item['descuento'];
        $subtotal         += $lineSubtotal;
    }

    $montoDescuento = $descuento > 0 ? round($subtotal * ($descuento / 100), 2) : 0;
    $total          = round($subtotal - $montoDescuento, 2);

    // 2. CREAR CABECERA DE VENTA (INSERT en tabla 'ventas')
    $venta = Venta::create([
        'numero_venta'   => $this->generarNumeroVenta(),  // VTA-2026-000042
        'cliente_id'     => $data['cliente_id'] ?? null,  // null = mostrador
        'metodo_pago_id' => $data['metodo_pago_id'],
        'usuario_id'     => auth('api')->id(),             // lee del JWT
        'subtotal'       => $subtotal,
        'descuento'      => $montoDescuento,
        'total'          => $total,
        'estado'         => 'completada',
    ]);

    // 3. CREAR DETALLES Y DESCONTAR STOCK (por cada producto)
    foreach ($data['items'] as $item) {
        $venta->detalles()->create([                  // INSERT en 'detalle_venta'
            'producto_id'     => $item['producto_id'],
            'cantidad'        => $item['cantidad'],
            'precio_unitario' => $item['precio_unitario'],
            'descuento'       => $item['descuento'],
            // 'subtotal' NO se manda — es columna COMPUTED STORED en PostgreSQL
        ]);

        Producto::find($item['producto_id'])      // busca el producto
            ->decrementarStock($item['cantidad']);  // descuenta stock
    }
    return $venta;
});
🟢 ¿Por qué DB::transaction()? Sin la transacción, si el servidor se cayera a mitad del foreach, podrían quedar algunos productos con stock descontado y otros no, o la venta creada sin todos sus detalles. Con la transacción, PostgreSQL garantiza que todo ocurre o nada ocurre.

PASO 7 — decrementarStock() en el modelo Producto

DB
Producto.php — decrementarStock() (líneas 94-102)
UPDATE directo en PostgreSQL. Más eficiente que el increment() estándar de Eloquent.
public function decrementarStock(int $cantidad): void
{
    // DB::table() hace UPDATE directo — más eficiente que Eloquent::decrement()
    // porque Eloquent haría: SELECT + validar + UPDATE (3 operaciones)
    // DB::table() hace: solo UPDATE (1 operación)
    DB::table('productos')
        ->where('id', $this->id)
        ->whereNull('deleted_at')        // respeta SoftDeletes
        ->update([
            'stock'      => DB::raw("GREATEST(stock - {$cantidad}, 0)"),
            //                ↑ función PostgreSQL: nunca deja el stock en negativo
            //                  GREATEST(3-5, 0) = GREATEST(-2, 0) = 0
            'updated_at' => now(),
        ]);
}

// El método inverso para cuando se anulan ventas o llegan compras:
public function incrementarStock(int $cantidad): void
{
    DB::table('productos')
        ->where('id', $this->id)
        ->update(['stock' => DB::raw("stock + {$cantidad}"), 'updated_at' => now()]);
}
🟢 GREATEST() — función de PostgreSQL GREATEST(valor1, valor2) retorna el mayor de los dos valores. Usarlo así: GREATEST(stock - 5, 0) garantiza que el stock nunca quede negativo aunque la validación previa fallara por alguna condición de carrera.

Generación del número de venta

BE
generarNumeroVenta() — líneas 260-274
Genera el correlativo anual: VTA-2026-000001, VTA-2026-000002…
private function generarNumeroVenta(): string
{
    $anio  = now()->format('Y');
    $ultimo = Venta::whereYear('created_at', $anio)->count();
    // count() = cuántas ventas hay este año → siguiente = count + 1

    return 'VTA-' . $anio . '-' . str_pad($ultimo + 1, 6, '0', STR_PAD_LEFT);
    // str_pad(42, 6, '0', LEFT) → '000042'
    // resultado final: 'VTA-2026-000042'
}

public function confirmarTransferencia(Venta $venta): JsonResponse
{
    if ($venta->estado !== 'pendiente') {
        return $this->error('Solo se pueden confirmar ventas en estado pendiente.', 422);
    }
    $venta->update(['estado' => 'completada']);
    // No hace falta tocar el stock — ya se descontó cuando se creó la venta pendiente
    return $this->success(new VentaResource($venta->fresh([...])), 'Transferencia confirmada.');
}

Preguntas típicas del docente y cómo responderlas

🎓
¿Por qué el estado del carrito está en PosScreen y no en CarritoActivo?

Porque tanto CarritoActivo como CatalogoProductos necesitan leer el mismo carrito. CatalogoProductos lo usa para mostrar el badge "2 en carrito". Si el estado viviera en CarritoActivo, el catálogo no lo vería. Al ponerlo en el padre (PosScreen), ambos hijos lo reciben como props. Este patrón se llama "lifting state up" — levantar el estado al ancestro común más cercano.

🎓
¿Para qué sirve DB::transaction() y qué pasa si no lo usas?

La transacción garantiza atomicidad: todas las operaciones dentro ocurren juntas o ninguna. Si el servidor se cayera después de insertar la venta pero antes de descontar el stock del producto 3, sin transacción quedaría un estado inconsistente: la venta existe pero el stock no se descontó. Con la transacción, PostgreSQL hace un ROLLBACK automático y nada queda a medias.

🎓
¿Qué es el Eager Loading con with('categoria')?

Es una técnica para evitar el problema N+1. Sin Eager Loading, Eloquent haría 1 query para los productos y luego 1 query adicional por cada producto para obtener su categoría (si hay 100 productos = 101 queries). Con with('categoria'), Eloquent hace solo 2 queries: una para los productos y una para todas las categorías de una sola vez. Laravel las cruza automáticamente en memoria.

🎓
¿Para qué usas useCallback en las funciones del carrito?

useCallback memoriza la función entre renders. Sin él, cada vez que PosScreen se re-renderiza (por cualquier cambio de estado), React recrearía todas las funciones como objetos nuevos. Como esas funciones se pasan como props a los hijos (CarritoActivo, CatalogoProductos), los hijos se re-renderizarían aunque los datos no cambiaran. Con useCallback, la referencia a la función es estable y React puede comparar que "es la misma función" y no re-renderizar innecesariamente.

🎓
¿Cómo se aplican las promociones? ¿El descuento lo calcula el backend o el frontend?

El frontend calcula el precio con descuento en CatalogoProductos usando getPromocionActiva() y calcularPrecioFinal(). Ese precio ya reducido llega al backend como precio_unitario. El backend no recalcula la promo — simplemente confía en el precio recibido. La responsabilidad de aplicar el descuento correcto está en el cliente. El backend sí tiene las promociones en base de datos (recibidas en /pos/init), así que el frontend trabaja con datos reales, no valores inventados.

🎓
¿Por qué el subtotal en detalle_venta no se envía desde la app?

Porque es una columna computed stored en PostgreSQL. Está definida en la migración con storedAs('(cantidad * precio_unitario) - descuento'). PostgreSQL la calcula automáticamente con cada INSERT o UPDATE. Esto garantiza que el valor matemático sea siempre correcto sin importar qué capa de la aplicación insertó el registro, y permite indexar esa columna para consultas de reportes rápidas.
